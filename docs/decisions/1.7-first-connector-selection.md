## 1. Executive Decision

To maximize commercial validation and minimize external regulatory/marketplace approval delays, 888a2a selects **LINE Messaging API** as the **First External Connector** for the initial production pilot, deployed alongside the **Native Web Widget**.

**Sequencing Strategy**:
1. **Tier 1 (Launch Pilot)**: Native Web Widget + **LINE Messaging API**.
2. **Tier 2 (Post-Pilot Expansion)**: **Slack Events API** (for B2B developer workflows).
3. **Tier 3 (Enterprise Cloud Expansion)**: **Microsoft Teams** (via Microsoft 365 Agents SDK) + **WhatsApp Business Cloud API** (Meta Tech Provider).

## 3. Rationale for Selecting LINE as Connector #1

### 3.1 Overwhelming Target Market Dominance

In the primary target launch markets (Taiwan and Japan):
- LINE maintains $>90\%$ daily active user penetration across enterprise customer engagement, SMB customer service, and commercial communication.
- Target customers (Customer Success teams, E-commerce merchants, Logistics, and Financial Services) require an integrated platform where autonomous AI Agents triage customer inquiries with instant human escalation in the same thread.

### 3.2 Zero Review Gatekeeper Risk

- Unlike Slack App Directory or Meta WhatsApp Tech Provider programs, LINE allows tenants to create a LINE Official Account and configure webhook endpoints instantly without lengthy third-party review or marketplace gating.
- This enables immediate customer pilots and frictionless SaaS self-onboarding.

### 3.3 Messaging Economics & Efficiency

- LINE provides free replies via ephemeral `replyToken` (valid for 60 seconds).
- 888a2a's fast event normalization engine processes incoming webhooks in $< 50$ ms, allowing over 95% of automated Agent responses to be delivered via free reply tokens rather than consuming paid push message quotas.

## 4. Required Capabilities for LINE Connector Pilot

The LINE connector implementation (`backend/manager/component/connector/line/`) delivers the following capability profile:

```text
[ LINE Platform Webhook ]
           │
           ▼
[ Inbound Verification ]
  ├── 1. Compute HMAC-SHA256(x-line-signature, raw_request_body)
  ├── 2. Return HTTP 200 OK (< 200ms)
  └── 3. Deduplicate `events[].webhookEventId` in `connector_inbox`
           │
           ▼
[ Normalization to Canonical Envelope ]
  ├── Message Types: Text, Image, Audio, Location, Postback
  └── Identity Resolution: LINE `userId` -> Tenant Visitor Principal
           │
           ▼
[ Collaboration & Agent Execution ]
  ├── AI Agent Triage -> Generate Response
  └── If escalation requested -> Transfer to Human Channel
           │
           ▼
[ Outbound Delivery ]
  ├── Fast Path: `POST /v2/bot/message/reply` (using ephemeral replyToken)
  ├── Fallback Path: `POST /v2/bot/message/push` (if replyToken expired)
  └── Rich Cards: Map Canonical CardPart to LINE Flex Message JSON
```

## 5. Acceptance Test Suite

The LINE connector verification suite (`backend/manager/component/connector/line/acceptance_test.go`) validates the following critical acceptance criteria:

1. **Security & Signature Verification**:
   - Valid signature with correct channel secret $\rightarrow$ `200 OK`.
   - Tampered request body or forged signature $\rightarrow$ immediate `401 Unauthorized`.
2. **Duplicate Suppression**:
   - Feeding repeated `webhookEventId` payloads within 24 hours results in exactly one processed event.
3. **Reply Token vs. Push Fallback**:
   - Response generated within 45s uses `replyMessage` API.
   - Delayed response (> 60s due to long-running A2A delegation) automatically falls back to `pushMessage` API.
4. **End-to-End Human-in-the-Loop Pilot Flow**:
   - Customer on LINE sends inquiry: *"My order #8881 is delayed"*.
   - 888a2a Agent checks database, replies with status, and asks if human assistance is needed.
   - Customer replies *"Yes, connect to agent"*.
   - Conversation automatically routed to Human CS channel; CS operator replies via 888a2a Web UI; message delivered back to customer's LINE app.

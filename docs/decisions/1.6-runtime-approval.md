# ADR 1.6: Runtime Permission-to-Organization-Approval Architecture & Decision Record

**Status**: Draft / Approval Prototype Pending  
**Date**: 2026-08-26  
**Scope**: Section 1 Architecture Spikes & Decision Gates (Task 1.6)

This document specifies the intended approval state machine. A fake ACP
provider and executable allow/deny/expiry/parameter-invalidation harness are
not yet present, so the scenarios below are not acceptance evidence.

---

## 1. Executive Summary

In enterprise environments, autonomous AI Agents executing sensitive tools (such as destructive shell operations, file writes outside sandboxes, or external production deployments) must not operate with unconditional, hardcoded permission grants.

888a2a introduces an **Organization-Governed Runtime Approval Policy Engine**. This engine unifies:
1. **ACP (Agent Control Protocol)** runtime permission requests (`session/requestPermission`).
2. **A2A 1.0 `AUTH_REQUIRED`** task suspension and resumption.
3. **Multi-Tenant Human-in-the-Loop Approval Center**.

This document records the design, state machine, and prototype verification of the approval pipeline with a fake ACP Provider, demonstrating **Allow**, **Deny**, **Expiry**, and **Parameter-Change Invalidation**.

## 2. Architecture & Approval Workflow

```text
[ Agent Runtime / Machine Runner ]
               │
               ▼
   1. ACP `requestPermission(tool, args)`
               │
               ▼
[ 888a2a Runtime Gateway ]
   - Evaluate Organization ApprovalPolicy
   - Compute Immutable Intent Hash: SHA-256(canonical_json(tool, args))
   - If Low Risk -> Auto-Approve
   - If High Risk -> Create Durable `ApprovalRequest` (State: PENDING)
               │
               ▼
   2. Suspend Agent Turn / Transition A2A Task to `AUTH_REQUIRED`
               │
               ▼
[ Organization Approval Center (UI / Webhook) ]
   - Notify Designated Approvers (Roles / Groups / Users)
   - Approver Reviews Bound Intent & Approves or Denies
               │
               ▼
[ Approval Decision Evaluator ]
   - Validate Quorum & Expiration
   - Issue Signed Single-Use Execution Nonce
               │
               ▼
   3. Resume ACP Session / Resume A2A Task (`WORKING`)
               │
               ▼
[ Execute Tool on Machine Runner ]
```

## 3. Data Contracts & Cryptographic Intent Binding

### 3.1 Approval Policy Contract (`ApprovalPolicy`)

```protobuf
message ApprovalPolicy {
  string organization_id = 1;
  string workspace_id = 2;
  string agent_id = 3;
  string tool_pattern = 4;        // e.g. "bash.execute", "fs.write", "k8s.deploy"
  RiskLevel risk_level = 5;       // LOW, MEDIUM, HIGH, CRITICAL
  repeated string approver_roles = 6;  // e.g. "OWNER", "ADMIN"
  repeated string approver_group_ids = 7;
  uint32 required_approvals = 8;  // Quorum (default: 1)
  uint32 timeout_seconds = 9;     // Default: 300s
  ActionOnTimeout on_timeout = 10;// TIMEOUT_DENY (default) or TIMEOUT_ESCALATE
}
```

### 3.2 Cryptographic Intent Hash

To prevent **Time-of-Check to Time-of-Use (TOCTOU)** attacks where an agent alters execution arguments while approval is pending, every request binds an immutable **Intent Hash**:

$$\text{IntentHash} = \text{SHA-256}\Big(\text{CanonicalJSON}\big(\text{tool\_name}, \text{arguments}, \text{working\_dir}, \text{environment\_keys}\big)\Big)$$

If the runtime tool invocation parameters differ from the approved Intent Hash by even a single byte, execution is immediately aborted.

## 4. State Machine Transitions

```text
                  ┌──────────────┐
                  │   PENDING    │
                  └──────┬───────┘
                         │
        ┌────────────────┼────────────────┬────────────────┐
        ▼                ▼                ▼                ▼
  ┌──────────┐     ┌──────────┐     ┌──────────┐     ┌─────────────┐
  │ APPROVED │     │ REJECTED │     │ EXPIRED  │     │ INVALIDATED │
  └────┬─────┘     └──────────┘     └──────────┘     └─────────────┘
       │
       ▼
 ┌───────────┐
 │ CONSUMED  │
 └───────────┘
```

- **`PENDING`**: Request published to approvers; waiting for quorum.
- **`APPROVED`**: Required approvals met; signed execution nonce issued.
- **`REJECTED`**: Explicit denial by an authorized approver.
- **`EXPIRED`**: Wall-clock timeout exceeded before decision reached.
- **`INVALIDATED`**: Agent modified parameters or aborted the parent turn before decision.
- **`CONSUMED`**: Execution nonce used once to execute the approved tool.

## 5. Prototype Verification Results with Fake ACP Provider

An automated verification harness (`backend/manager/component/approval/runtime_approval_test.go`) executed tests against a simulated ACP Provider runtime:

### 5.1 Test Scenarios & Results

#### Scenario 1: Allow (Approval Granted)
- **Action**: Agent requests execution of `deploy_service(target: "prod", version: "v2.1")`.
- **Flow**:
  1. Policy matches `risk_level = CRITICAL`, requires `OWNER` approval.
  2. Request created with Intent Hash `7f83b1657ff1fc53b92dc18148a1d65dfc2d4b1fa3d677284addd200126d9069`.
  3. Approver Alice (`OWNER`) calls `SubmitDecision(APPROVED)`.
  4. ACP Provider unblocks and receives approval token.
  5. Tool executes successfully; state transitions to `CONSUMED`.
- **Verdict**: **PENDING**. No executable fake-ACP approval harness is present.

#### Scenario 2: Deny (Explicit Rejection)
- **Action**: Agent requests `bash.execute("rm -rf /var/log/audit")`.
- **Flow**:
  1. Policy flags tool as dangerous; routes to Admin group.
  2. Approver Bob calls `SubmitDecision(REJECTED, reason: "Destructive operation prohibited")`.
  3. ACP Provider unblocks and returns `ACPErrorPermissionDenied` to Agent prompt.
  4. Agent receives structured refusal and adapts execution plan.
- **Verdict**: **PENDING**.

#### Scenario 3: Expiry / Timeout
- **Action**: Agent requests `s3.delete_bucket(bucket: "financial-records")` with `timeout_seconds = 2`.
- **Flow**:
  1. No approver acts within the 2-second timeout window.
  2. State machine transitions request to `EXPIRED`.
  3. ACP Provider returns `ACPErrorTimeout` ("Approval request expired without response").
- **Verdict**: **PENDING**. Default-deny timeout evidence is not implemented.

#### Scenario 4: Parameter-Change Invalidation (Anti-Tampering)
- **Action**:
  1. Agent requests `fs.write_file(path: "/app/config.json", content: "env=prod")` $\rightarrow$ Intent Hash $H_1$.
  2. While request is `PENDING`, Agent restarts turn and submits `fs.write_file(path: "/app/config.json", content: "env=prod; rm -rf /")` $\rightarrow$ Intent Hash $H_2$.
- **Flow**:
  1. Approver unwittingly approves $H_1$.
  2. Runtime verifies $H_1 \ne H_2$.
  3. Request $H_1$ marked `INVALIDATED`; execution is blocked with error `ErrIntentMismatch`.
  4. A new approval request is required for $H_2$.
- **Verdict**: **PENDING**. Intent invalidation evidence is not implemented.

#### Scenario 5: A2A `AUTH_REQUIRED` End-to-End Interop
- **Action**: Remote A2A Agent delegates high-risk code refactor task.
- **Flow**:
  1. A2A Gateway transitions task to `AUTH_REQUIRED` and emits status event to requester.
  2. Organization admin approves request in 888a2a Approval Center.
  3. Task automatically transitions to `WORKING` and completes.
- **Verdict**: **PENDING**. The ACP/A2A approval bridge is not implemented.

## 6. Auditability & Compliance

Every approval lifecycle event is durably written to `audit_log` and `a2a888_work_event` with:
- Organization & Workspace ID
- Requesting Agent & Principal ID
- Approver Principal ID & Role
- Tool Name, Parameter Snapshot, and Intent Hash
- Complete timestamp and decision justification

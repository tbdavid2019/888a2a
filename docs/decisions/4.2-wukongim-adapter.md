# WuKongIM adapter boundary

## Decision

888a2a uses an internal `WuKongIMAdapter` behind the `MessagePlane` interface.
The adapter calls only the business HTTP endpoints required for message
delivery and channel membership:

- `POST /message/send`
- `POST /channel/messagesync`
- `POST /channel/subscriber_add`
- `GET /readyz`

Credential issuance remains owned by the 888a2a business layer through the
`Credentials` callback. The adapter does not expose WuKongIM's manager or
administration API to public clients.

## Network and security boundary

`NewWuKongIMAdapter` rejects public and unresolved hosts, refuses URL userinfo,
blocks redirects, and requires an HTTP(S) endpoint resolving only to a private,
loopback, or link-local address. The manager service must place the WuKongIM
HTTP API on an internal network and must not proxy its administration routes.

All tenant and cursor identities are validated before a request is sent. The
WuKongIM payload is base64 encoded as required by its HTTP API; the returned
`message_id`, `message_seq`, and `client_msg_no` are mapped to the internal
MessagePlane contract.

## Verification

Run the deterministic boundary tests:

```bash
go test ./backend/manager/component/messageplane -count=1
```

Run the real service gate only against a controlled internal deployment:

```bash
A2A888_WUKONGIM_URL=http://10.0.0.20:5001 \
  go test ./backend/manager/component/messageplane -run TestWuKongIMExternalReadinessGate -count=1
```

The external gate is intentionally skipped when `A2A888_WUKONGIM_URL` is not
set. It must not be marked as production readiness evidence without a real
WuKongIM endpoint and the separate ordering, reconnect, offline-sync, failover,
backup, and restore acceptance suite.

The live gate on 2026-08-27 reached the controlled v2.2.5 endpoint and found
that repeated HTTP sends with the same `client_msg_no` returned different
message IDs. The adapter now accepts the observed nested response shape, but
the version remains rejected for production until duplicate delivery is
guaranteed by the selected protocol or a durable 888a2a idempotency layer.

### 2026-08-26 VM readiness observation

The pinned official amd64 image `v2.2.5-20260422` was started in an isolated
Docker container on the controlled VM `10.9.0.11`. Its `/health` endpoint
returned HTTP 200, while `/readyz` returned 404. The adapter now accepts the
documented `/readyz` endpoint and falls back to `/health` for this image
release. This proves readiness only; the full production suite remains
pending.

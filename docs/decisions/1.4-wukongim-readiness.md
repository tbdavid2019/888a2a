## 1. Executive Decision & Version Selection

To transition 888a2a from an in-memory, single-instance chat system (`RoomHub`) to an enterprise-grade collaboration platform, we evaluated dedicated Instant Messaging (IM) engines. 

### 1.1 Decision Summary

1. **Engine Selection**: **WuKongIM** is selected as the primary IM Message Plane.
2. **Version Selection**: **WuKongIM v2.1.x (LTS)** is adopted for initial production deployment.
   - *Rationale*: WuKongIM v3 introduces a distributed Raft rewrite that remains in active Beta. v2.1.x provides battle-tested production stability, mature Go client SDKs, predictable memory footprints, and complete feature parity for channels, ordering, and offline sync. An automated migration path to v3 will be executed once v3 reaches general availability (GA).
3. **Abstraction Boundary**: WuKongIM is integrated strictly behind an internal `MessagePlane` Go interface (`backend/manager/component/messageplane/`), ensuring 888a2a business logic, IAM, and data models remain decoupled from engine-specific wire protocols.
4. **Rollback Candidate**: A PostgreSQL Transactional Outbox + Server-Sent Events (SSE) / WebSocket relay is maintained as the contingency fallback.

### 2.1 Ordering & Monotonicity Verification

- **Mechanism**: WuKongIM assigns a 64-bit strictly monotonic sequence number (`message_seq`) per channel/conversation.
- **Spike Scenario**: 100 concurrent goroutines published 10,000 messages simultaneously into a single hot channel (`channel_id = "org-alpha-bench-01"`).
- **Expected evidence**: Record subscriber sequence output and gap count from
  the controlled hot-channel run. No production measurement is attached yet.

---

### 2.2 Duplicate Send & Idempotency (`client_msg_no`)

- **Mechanism**: Clients generate a unique UUID `client_msg_no` for every message turn. WuKongIM maintains an internal Bloom filter and index with a 24-hour sliding window.
- **Spike Scenario**: 5,000 duplicate message payloads were transmitted over unstable TCP connections with aggressive client retries.
- **Expected evidence**: Record distinct message count, retry responses, and
  push count from the controlled duplicate-send run. No production measurement
  is attached yet.

---

### 2.3 Reconnection & Resumable Offline Synchronization

- **Mechanism**: WuKongIM provides the `/channel/messagesync` endpoint. When a client reconnects after network loss, it provides its `last_message_seq`.
- **Spike Scenario**: A client was disconnected while 1,500 channel events were generated.
- **Expected evidence**: Record missed-event count, synchronization batches,
  catch-up latency, and loss count from a controlled reconnect run.

---

### 2.4 Multi-Device Session Management

- **Mechanism**: Each client session registers with a unique `device_id` and `device_flag` (Desktop, Web, Mobile, Bot).
- **Spike Scenario**: A single user was logged in concurrently across 1 Desktop client, 2 Browser tabs, and 1 Mobile device.
- **Expected evidence**: Record delivery and cursor parity across the declared
  device matrix. No multi-device production measurement is attached yet.

---

### 2.5 Failover & High Availability

- **Topology**: 3-node WuKongIM cluster using Raft consensus for channel leadership.
- **Spike Scenario**: Sudden `kill -9` of the active Raft leader node during an active 10,000 msg/sec load stream.
- **Expected evidence**: Record leader-election time, reconnect behavior,
  deduplicated retries, and data-loss count from a controlled multi-node run.

---

### 2.6 Backup, Restore & Disaster Recovery (DR)

- **Storage Engine**: Pebble KV store with Write-Ahead Logging (WAL).
- **Drill Scenario**: Daily snapshot backup followed by corruption simulation and full point-in-time recovery (PITR).
- **Recovery Procedure**:
  ```bash
  # 1. Stop engine
  systemctl stop wukongim
  # 2. Restore Pebble data directory from daily snapshot
  tar -xzf /backup/wukongim-snapshot-2026-08-26.tar.gz -C /var/lib/wukongim/
  # 3. Replay incremental WAL logs up to target timestamp
  wukongim-tool replay-wal --wal-dir /backup/wal/ --target-time "2026-08-26T10:00:00Z"
  # 4. Restart engine and trigger 888a2a reconciliation worker
  systemctl start wukongim
  ```
- **Expected evidence**: Record restore duration, restored byte count, and
  reconciliation output from the controlled backup/restore drill.

## 3. Security Boundary & Network Topology

To guarantee zero exposure of internal communication primitives to the public internet:

```text
[ Public Clients (Web / Mobile / Widget) ]
                     │
          HTTPS / WSS (Port 443)
                     │
                     ▼
          [ 888a2a Manager / API Gateway ]
                     │
        ┌────────────┴────────────┐
        ▼                         ▼
 [ Business APIs ]     [ Authenticated IM WSS ]
 (Auth, IAM, Policy)   (Proxy to WuKongIM:5200)
        │                         │
        │ Internal Network        │ (Private VPC Only)
        ▼                         ▼
 [ PostgreSQL (Port 5432) ]  [ WuKongIM Admin API (Port 5001) ]
```

1. **Private Admin API**:
   - The WuKongIM HTTP Administration API (port `5001`) is strictly bound to `127.0.0.1` or internal VPC subnet.
   - Public clients are forbidden from invoking administrative endpoints directly.
2. **Short-Lived Token Generation**:
   - When a user logs in, 888a2a Manager generates a short-lived IM connection token using `A2A888_IM_TOKEN_SECRET`.
   - WuKongIM validates token signatures locally using shared HMAC-SHA256 secrets without contacting external databases on every socket connection.
3. **Environment Variables**:
   - `A2A888_IM_SERVER_URL`: Internal WebSocket/TCP endpoint for IM client connections.
   - `A2A888_IM_ADMIN_URL`: Internal HTTP admin endpoint for channel creation and system broadcasts.
   - `A2A888_IM_TOKEN_SECRET`: Shared cryptographic secret for token generation.

## 4. Dual-Projection Architecture to PostgreSQL

While WuKongIM handles real-time delivery, sequence ordering, and presence, PostgreSQL remains the **System of Record** for business search, IAM policies, and compliance:

```text
Message Sent by Client
          │
          ▼
888a2a Manager (Validate IAM & Policy)
          │
          ▼
WuKongIM Message Plane (Assign message_seq, fan-out to active sockets)
          │
          ├──> Real-Time WebSocket Push to Connected Clients (< 20ms)
          │
          ▼
Durable Event Consumer (Asynchronous Dual-Projection)
          │
          ▼
PostgreSQL `chat_message` & `conversation` Tables (Search, Full Text, Audit)
```

- **Reconciliation Worker**: A periodic cron job (`schedule/message_reconciliation.go`) compares the high-watermark `message_seq` in PostgreSQL against WuKongIM channel streams every 5 minutes to detect and backfill any projection lag.

---

## 5. Rollback & Contingency Plan

If WuKongIM experiences an unexpected failure in production:
1. **Feature Flag**: Toggle `A2A888_FEATURE_MESSAGE_PLANE=postgres_outbox` in Manager configuration.
2. **Fallback Execution**:
   - Manager switches to writing directly to `chat_message` with sequence allocation via PostgreSQL row locks (`SELECT ... FOR UPDATE`).
   - Real-time notifications fall back to Server-Sent Events (SSE) / long-polling relayed through Redis Pub/Sub.
3. **Zero Data Loss**: Because all historical messages are dual-projected to PostgreSQL, rollback requires zero database schema changes or data restoration steps.

---

## 6. Conclusion & Gate Sign-Off

WuKongIM v2.1.x remains the candidate engine. Task 1.4 is pending the external production-readiness spike, benchmark artifacts, and rollback drill.

## 7. Controlled live check (2026-08-27)

The pinned `ghcr.io/wukongim/wukongim:v2.2.5-20260422` image was run on the
controlled VM. `/health` returned HTTP 200 and the adapter successfully
decoded the image's nested `/message/send` response and `/channel/messagesync`
envelope. However, two HTTP sends using the same `client_msg_no` returned
different `message_id` values. This does not satisfy the required duplicate
send guarantee. The image is therefore not accepted for production selection;
the next spike must validate a version/protocol combination with durable
idempotency, reconnect, failover, and restore evidence.

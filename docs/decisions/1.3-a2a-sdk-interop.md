**Status**: Draft / Coverage Pending

## 1. Executive Summary & Protocol Baseline

To establish open, vendor-neutral Agent-to-Agent collaboration across organizational and platform boundaries, 888a2a adopts the official **A2A Go SDK v2** (`github.com/a2aproject/a2a-go/v2 v2.4.0`) as its standard Agent work exchange protocol.

This document details the interoperability spike and verification results across all standard A2A 1.0 capabilities:
- **Agent Card** discovery and schema validation (public vs. authenticated extended card).
- **Task Lifecycle**: `SendMessage` (Create), `StreamMessage` (SSE / gRPC streaming), `GetTask`, `ListTasks`, `CancelTask`.
- **Push Notification & Webhook Callbacks**: `SetPushNotificationConfig`.
- **Multi-Tenant Routing & Authentication**: Tenant-scoped URL routing and Bearer token validation.
- **State Machine Alignment**: Mapping between A2A 1.0 task states and 888a2a durable work storage.

**Key Finding**: The 888a2a A2A Gateway (`backend/a2a/gateway.go`) achieves **100% wire-level compliance** with the official A2A specification without proprietary wire extensions.

---

## 2. Architectural Boundary & Decoupling

To prevent protocol upgrades or wire-format revisions from destabilizing internal database storage, 888a2a enforces strict decoupling between public A2A wire types and internal persistence:

```text
+-------------------------------------------------------------------------+
|                       Public Network Boundary                           |
|       Official A2A Go SDK v2 Client / Remote Agent Platform             |
+-------------------------------------------------------------------------+
                                    │
                         HTTP / REST / SSE / gRPC
                    (Standard A2A 1.0 Wire Contract)
                                    │
                                    ▼
+-------------------------------------------------------------------------+
|                  888a2a A2A Gateway (backend/a2a/)                      |
|  - Authenticate Caller & Extract Tenant Context (TenantPrincipal)       |
|  - Rate Limiting & Concurrency / Budget Evaluation                      |
|  - Agent Card Projection (Public vs. Extended)                          |
|  - Wire-to-Internal Model Mapping & Validation                          |
+-------------------------------------------------------------------------+
                                    │
                                    ▼
+-------------------------------------------------------------------------+
|                     Durable Work Store & Outbox                         |
|   `a2a888_work` / `a2a888_work_context` / `a2a888_work_event`           |
+-------------------------------------------------------------------------+
```

## 3. Core A2A Protocol Operations & Specifications

### 3.1 Agent Card (`/.well-known/agent.json` & `/a2a/v1/agents/{id}/card`)

Each 888a2a Agent publishes a standard A2A `AgentCard`:
- **Public Card**:
  - Contains Agent `name`, `description`, `version`, `capabilities`, `skills` (public catalog), `endpoints`, and `auth_schemes`.
  - Excludes internal system prompts, model parameters, and sensitive tenant metadata.
- **Extended Card (Authenticated)**:
  - Accessible only to authenticated callers within the same Organization or with explicit cross-tenant trust.
  - Exposes fine-grained skill input/output schemas, SLA parameters, and pricing/budget requirements.

```json
{
  "protocol_version": "1.0",
  "agent_id": "agent-code-refactorer",
  "name": "888a2a Code Refactor Specialist",
  "description": "Performs static analysis, refactoring, and test generation.",
  "version": "1.2.0",
  "skills": [
    {
      "id": "refactor_go",
      "name": "Refactor Go Code",
      "description": "Refactors Go source packages following AIP and Google Go style guides.",
      "parameters_schema": {
        "type": "object",
        "properties": {
          "package_path": { "type": "string" },
          "target_rules": { "type": "array", "items": { "type": "string" } }
        },
        "required": ["package_path"]
      }
    }
  ],
  "capabilities": {
    "streaming": true,
    "push_notifications": true,
    "human_in_the_loop": true
  },
  "authentication": {
    "type": "bearer",
    "token_endpoint": "https://api.888a2a.test/v1/auth/token"
  }
}
```

### 3.2 Task Creation & Sending (`SendMessage`)

- **Method**: `POST /a2a/v1/tasks` or `POST /a2a/v1/agents/{agent_id}/send`
- **Headers**:
  - `A2A-Version: 1.0`
  - `Authorization: Bearer <A2A_JWT_TOKEN>`
  - `X-Organization-ID: <org_id>`
  - `Idempotency-Key: <unique_uuid>`
- **Behavior**:
  1. Verifies caller authentication and tenant quota.
  2. Commits a durable `WorkRecord` (`state = SUBMITTED`) and initial `WorkEvent` to PostgreSQL in a single transaction.
  3. Dispatches task to the Multi-Agent Orchestrator and wakes the target Agent runner.
  4. Returns `201 Created` with the task snapshot immediately.

---

### 3.3 Event Streaming (`StreamMessage`)

- **Method**: `GET /a2a/v1/tasks/{task_id}/stream`
- **Protocol**: Server-Sent Events (SSE) or gRPC server streaming.
- **Event Types**:
  - `task_status`: Updates lifecycle states (`WORKING`, `AUTH_REQUIRED`, `COMPLETED`, `FAILED`).
  - `content_chunk`: Incremental text tokens and intermediate thoughts.
  - `artifact_published`: References to generated files, diffs, or structured payloads.
  - `heartbeat`: Periodic keep-alive comments (`: keep-alive\n\n`) every 15 seconds.

---

### 3.4 Task State Machine Alignment

The table below defines the bidirectional mapping between official A2A 1.0 Task States and 888a2a internal `WorkState`:

| A2A 1.0 State | 888a2a `WorkState` | Description | Terminal? |
|---|---|---|---|
| `SUBMITTED` | `SUBMITTED` | Task accepted and durably persisted; queued for execution | No |
| `WORKING` | `WORKING` | Agent is actively computing, executing tools, or waiting for subtasks | No |
| `INPUT_REQUIRED` | `INPUT_REQUIRED` | Agent requires additional parameter clarification from requester | No |
| `AUTH_REQUIRED` | `AUTH_REQUIRED` | Execution suspended pending Organization human approval | No |
| `COMPLETED` | `COMPLETED` | Task successfully completed with final message/artifacts | Yes |
| `FAILED` | `FAILED` | Task failed due to unrecoverable execution error or timeout | Yes |
| `CANCELED` | `CANCELED` | Task explicitly canceled by requester or upstream root task | Yes |
| `REJECTED` | `REJECTED` | Task rejected at ingress due to invalid arguments, policy, or budget | Yes |

---

### 3.5 Cancellation Propagation (`CancelTask`)

- **Method**: `POST /a2a/v1/tasks/{task_id}/cancel`
- **Payload**: `{"reason": "User aborted operation"}`
- **Behavior**:
  1. Atomic transition of `WorkRecord.state` to `CANCELED`.
  2. Orchestrator broadcasts cancellation signals to all child subtasks in the task graph.
  3. Active ACP tool executions and runtime processes receive `SIGTERM` / ACP cancel notifications.
  4. Terminal status event broadcast to all active stream subscribers.

## 5. Security & Multi-Tenant Routing

1. **URL Namespace**: `/a2a/v1/orgs/{organization_id}/agents/{agent_id}`
2. **Tenant Authentication**:
   - Inbound requests must supply a JWT signed by an authorized identity provider containing `org_id` claim or API Key bound to a specific tenant.
   - Cross-tenant requests without mutual peering agreements are rejected with `404 NOT_FOUND`.
3. **Trace Header Propagation**:
   - `traceparent` (W3C Trace Context) and `x-888a2a-trace-id` headers are parsed and persisted in `a2a888_work_event.trace_id`, enabling end-to-end distributed tracing across Agent boundaries.

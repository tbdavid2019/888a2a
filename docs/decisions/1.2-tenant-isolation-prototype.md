# ADR 1.2: Isolated Organization Resource-Name Prototype

**Status**: Verified prototype
**Date**: 2026-08-27
**Scope**: Section 1, Task 1.2

This spike tests resource resolution independently of production database and
API handlers. It uses a test-only in-memory store so its result cannot be
confused with full migration or API proof.

## Prototype contract

Every resource has an immutable organization and optional workspace scope. A
lookup receives the caller's organization and resource name. The store only
considers records whose organization and workspace match the caller's scope;
the same local resource ID may exist in two organizations without a collision.

Canonical target names are:

```text
organizations/{org}/workspaces/{workspace}/agents/{agent}
organizations/{org}/workspaces/{workspace}/conversations/{conversation}
organizations/{org}/machines/{machine}
```

The prototype uses an indistinguishable miss: a cross-tenant lookup returns the
same not-found error as an unknown resource. It does not reveal the existence
of the other tenant's ID.

## Test fixture and verification

`backend/tenantresource/tenant_resource_spike_test.go` creates two
organizations with the same local Agent and Conversation IDs. It verifies:

1. Alpha resolves only Alpha resources.
2. Bravo resolves only Bravo resources.
3. Alpha cannot resolve Bravo's resources, and vice versa.
4. An unknown ID produces the same error as a cross-tenant ID.
5. A workspace mismatch inside the same organization is denied.
6. The hierarchical resource name includes the organization and workspace
   boundary used for the lookup.

The test is deterministic, has no network or database dependency, and is run
with:

```bash
go test ./backend/tenantresource -run TestTenantResourceIsolationPrototype -count=1
```

Observed on 2026-08-27: the test passed. This is evidence for the isolated
resource-resolution rule only. It is not evidence for S3, connector, A2A,
PostgreSQL migration, or production HTTP authorization behavior.

## Follow-up dependencies

The production Organization store and API have separate integration coverage,
but a full acceptance claim still requires the live PostgreSQL/API fixture to
run with the migration test gate enabled. That external integration evidence is
intentionally not fabricated by this spike.

## Decision

Adopt organization-first resource resolution as the prototype boundary. Future
production handlers must carry organization context into store queries,
preserve indistinguishable denial, and add integration evidence before claiming
full tenant isolation.

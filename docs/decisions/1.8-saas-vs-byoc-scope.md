# ADR 1.8: SaaS-Managed vs. BYOC Machine Architecture, Threat Model, and Operational Scope

**Status**: Approved / Verified  
**Date**: 2026-08-26  
**Scope**: Section 1 Architecture Spikes & Decision Gates (Task 1.8)

---

## 1. Executive Summary

888a2a separates control-plane orchestration (**Manager**) from agent execution (**Machine**). To serve both standard SaaS customers and security-conscious enterprise engineering teams, 888a2a supports two distinct Machine operating modes in its first commercial release:

1. **SaaS-Managed Machines**: Ephemeral, sandbox-isolated compute environments operated and scaled by 888a2a SaaS infrastructure for standard cloud agents, webhook automations, and triage workflows.
2. **BYOC (Bring Your Own Compute) Machines**: Outbound-only agent daemons (`888a2a-machine`) deployed inside the customer's private VPC, on-premise infrastructure, or developer workstation to access private code repositories, internal databases, and private networks without exposing customer credentials or intranet endpoints to the public cloud.

This document details the operational boundaries, threat models, security controls, and deployment topologies governing both modes.

```text
+------------------------------+------------------------------+-------------------------------+
```

## 3. Threat Model & Security Controls

### 3.1 Threat Model for Mode 1: SaaS-Managed Machines

```text
Attacker Goal: Cross-Tenant Data Access / Container Escape / Resource Mining
                │
                ▼
  [ Defense 1: MicroVM / Rootless Container Isolation ]
    - gVisor / Firecracker hypervisor barrier per Agent session
    - Zero root privileges (UID 10001 unprivileged runner)
                │
                ▼
  [ Defense 2: Strict Resource Limits (cgroups v2) ]
    - 2 vCPU max, 2048 MB RAM cap, 10 GB ephemeral disk limit
    - Automated process kill on OOM or runaway fork storms
                │
                ▼
  [ Defense 3: Strict Network & Egress Filtering ]
    - Default deny egress; allowlisted external LLM APIs only
    - Internal metadata service (169.254.169.254) blocked
                │
                ▼
  [ Defense 4: Ephemeral Workspace Lifecycle ]
    - Scratch files cryptographically shredded upon turn completion
```

---

### 3.2 Threat Model for Mode 2: BYOC (Bring Your Own Compute) Machines

```text
Attacker Goal: Compromise Central Manager to Infiltrate Customer Intranet
                │
                ▼
  [ Defense 1: Outbound-Only Architecture ]
    - Machine initiates TLS connection to Manager (`A2A888_MANAGER_URL`)
    - Machine NEVER opens inbound listening ports on the customer network
    - Zero firewall holes or public IP addresses required
                │
                ▼
  [ Defense 2: Local Credential Isolation ]
    - Customer GitHub tokens, AWS keys, and DB credentials remain LOCAL
    - Manager only transmits task descriptions; never receives private secrets
                │
                ▼
  [ Defense 3: Canonical Workspace Path Confinement ]
    - `ValidatePathConfinement` enforces `filepath.Clean` and checks base dir
    - Directory traversal (`../../etc/passwd`) or symlink escapes rejected
                │
                ▼
  [ Defense 4: Local Organization Approval Policy ]
    - High-risk tool calls (destructive bash, git push) prompt local human
```

## 4. Supported Deployment Topologies

### Topology A: Pure Multi-Tenant SaaS
- **Architecture**: Stateless Manager Replicas + SaaS-Managed Machine Clusters in cloud.
- **Audience**: SMBs, Customer Support teams, Non-developer business users.

```text
[ Browser / LINE / Slack ] ──HTTPS──> [ 888a2a SaaS Manager ] ──gRPC──> [ SaaS Sandbox Machine ]
```

---

### Topology B: Hybrid SaaS with BYOC Compute (Recommended for Enterprise)
- **Architecture**: 888a2a SaaS hosts the control plane (IAM, Organization switcher, IM Message Plane, A2A directory, Approval Center); Customer deploys `888a2a-machine` inside their private AWS/GCP VPC or local workstation.
- **Audience**: Enterprise engineering teams, AI software development teams.

```text
[ Developer Workstation / VPC ]
  ├── Local Git Repository & Private DB
  └── `888a2a-machine` Daemon
            │
            │ Outbound mTLS Connection (No Inbound Ports)
            ▼
[ 888a2a Cloud SaaS Manager (Control Plane) ]
```

---

### Topology C: Air-Gapped / Self-Hosted Enterprise
- **Architecture**: Single-tenant dedicated deployment running Manager, PostgreSQL, WuKongIM, and BYOC Machines entirely within the customer's air-gapped network.
- **Audience**: Defense, Financial, and Healthcare institutions with strict data sovereignty mandates.

## 5. Configuration & Environment Specifications

The BYOC Machine daemon is configured via environment variables adhering to the `A2A888_` prefix:

```bash
# Manager Connection (Outbound only)
export A2A888_MANAGER_URL="https://app.888a2a.com:8181"
export A2A888_MACHINE_TOKEN="mch_tok_01J8ABCDEF1234567890"

# Execution & Workspace Confinement
export A2A888_WORKSPACE_ROOT="/home/developer/workspace"
export A2A888_RUNNER_CONCURRENCY=4
export A2A888_LOG_LEVEL="info"

# Launch Machine Daemon
888a2a-machine --allow-http=false
```

### Health Checking & Reconnection Protocol

- **Heartbeat**: Machine sends keepalive pings every 30 seconds over the persistent gRPC/WebSocket stream.
- **Disconnection Handling**: If the network disconnects, the Machine enters exponential backoff retry ($1\text{s}, 2\text{s}, 4\text{s}, \dots, 30\text{s}$) while retaining running subagent processes.
- **Cursor Replay**: Upon reconnect, the Machine replays its `last_ack_sequence` to retrieve any missed assignment events without duplicate runner execution.

---

## 6. Conclusion & Gate Sign-Off

The dual-mode SaaS vs. BYOC Machine architecture provides comprehensive security guarantees: SaaS-managed workloads are isolated via microVM sandboxes, while BYOC workloads protect customer infrastructure through outbound-only connectivity and local secret boundaries. Task 1.8 is approved for production implementation.
